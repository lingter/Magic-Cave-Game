## 2. 当前需要修正的清单

### R01｜P1｜死亡结算遇到不可清理的满仓时，没有恢复出口

**状态：源码确认，并通过 Unity MCP 对内存对象调用实际业务方法复现。**

当前规格要求“满仓暂停入库，整理仓库后继续”，同时允许新增装备、精华入仓，但暂不开放它们的出售、捐赠或下局携带。两条规则叠加后，整理操作不能保证腾出容量。

触发步骤：

1. 仓库已扩容10次，容量为600；600件均为不能出售的新增物品，例如力量精华。
2. 玩家在另一次探索中死亡，背包存在至少1件物品，系统自动选入失败带出。
3. 确认结算被容量检查拒绝；出售精华不允许，扩容达到上限。
4. 失败结算不允许取消或删减自动选取的物品；待结算状态又阻止继续和开始新局。

这不是要求立即开放装备出售，而是现有“满仓可恢复”承诺缺少可执行的出口。容量未满级但金币不足、且没有其他可用腾挪手段时，也存在同类风险。

| 现有逻辑 | 位置 |
|---|---|
| 容量检查先于入库与金币奖励 | `PrototypeStore.cs:138`，`CommitSettlement` |
| 失败选择不可修改／取消 | `PrototypeStore.cs:123`、`130` |
| 待结算阻止继续／丢弃旧局 | `PrototypeStore.cs:99`、`107` |
| 扩容上限10；出售仅允许前4类旧物品 | `PrototypeStore.cs:228`、`235` |
| 界面仅提供出售旧物品、捐赠遗物、扩容 | `PrototypeTown.cs:351`，`DrawTownWarehouse` |
| 失败结算不能返回探索 | `PrototypeInterface.cs:232`，`DrawSettlement` |

代码路径均位于 `Assets/MagicCavePrototype/Runtime/`。

**修正目标：** 所有合法满仓状态均能在不重置存档的情况下结束待结算；不重复发放物品、金币、声望，也不静默删除物品。

**建议方案，尚非新增规则：** 为仓库中的不可出售物品提供明确的放弃操作及损失提示，从而保留当前自动带出排序和出售范围。另一种方案是结算溢出处理，但涉及带出数量／所有权，必须先补相应规格。不能仅把报错改为“请整理仓库”，也不能绕过容量校验。

**修复后验收：** 满仓全为精华、满仓全为装备、容量不足以容纳全部失败带出三种情形均可恢复；退出重进后仍能处理；重复确认不重复奖励；未明确放弃的旧物品和未入库物品保留。覆盖主动结算、失败结算和已提交记录恢复。

现有 `Tests/Editor/TownProgressionTests.cs:99` 的满仓测试使用可出售的矿石，能通过出售恢复，尚不能覆盖上述死路。修复时应补这一针对性用例。

### R02｜P2｜背包标题没有说明装备不可堆叠

**状态：界面源码与实际容量函数确认。**

`PrototypeInterface.cs:317` 显示“每格最多20件”。但 `PrototypeData.cs:193` 的 `StackLimit` 对装备返回1，对材料及消耗品返回20；属性v1第11.2节也明确这一区别。现有措辞容易使玩家误以为装备可以合并到同一格。

**修正目标：** 改为“装备每格1件；材料／消耗品同类每格最多20件”，保留20格总容量；同步相关帮助文字。无需改变物品堆叠逻辑。

**验收：** 装备和材料使用同一套明确说明；窄窗口／当前游戏分辨率下文字不截断。属于低影响文案修正，无需为字符串新增逻辑测试。

### R03｜P2｜仓库把同类装备合计，却只展示第一件的属性快照

**状态：源码确认；问题在同类装备存在不同历史配置时触发，未宣称当前玩家仓库已有这种混合库存。**

`PrototypeTown.cs:378` 统计全部同类装备数量，随后 `FirstOrDefault` 取第一件并展示属性。存储层却按实例保留各局的 `EquipmentDefinition` 快照（`PrototypeStore.cs:156`）。调整试配后，旧局与新局取得的同名装备可以拥有不同属性，界面仍用一行属性代表整个数量，无法查看其余差异。

**修正目标：** 按属性快照分组，或允许展开逐件查看；每组数量和显示属性必须对应。保留原有实例快照，不为统一展示而把旧装备改成最新配置。

**验收：** 两件同类、不同基础ATK或修正系数的装备均可查看正确属性；相同配置可以合并显示；重载后数量和属性不变。此项无需同时开放装备出售或下局携入。
